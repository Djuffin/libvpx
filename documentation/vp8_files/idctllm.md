# `vp8/common/idctllm.c` — the 4x4 inverse transforms

## Role in the decoder

This file holds the *kernels* that turn a 4x4 block of dequantized
coefficients back into a 4x4 block of residual pixel values, and that
invert the second-order ("Y2") Walsh–Hadamard transform sitting in
front of the 16 luma DCs. They are the bottom of VP8's reconstruction
pipeline — entropy decode produces 16-bit `qcoeff`s, dequantization
scales them into `dqcoeff`, and the routines here do the actual
mathematical inversion of the forward transform that the encoder
applied.

The cryptic `llm` in the file name stands for *low/low math*: a purely
integer, branch-free, 16-bit fixed-point reference that the VP8 spec
defines bit-exactly. There is exactly one normative answer for every
input; the SIMD implementations under `vp8/common/arm/`,
`vp8/common/x86/`, etc., are required to match this C reference to
the bit. The constants and structure here trace directly to RFC 6386
§14.1 ("Dequantization") and §14.4 ("Summation of Predictor and
Residue") via §14.3 ("Implementation of the WHT Inversion") and
§14.2 ("Inverse Transforms").

Four routines live in the file, all C reference versions of functions
declared in the generated `vp8_rtcd.h`:

| Symbol                          | RFC 6386 section | Purpose                                                       |
|---------------------------------|------------------|---------------------------------------------------------------|
| `vp8_short_idct4x4llm_c`        | §14.2            | Full 4x4 IDCT, accumulated into a predictor.                  |
| `vp8_dc_only_idct_add_c`        | §14.2 (fast path)| Fast path when only the DC coefficient is non-zero.           |
| `vp8_short_inv_walsh4x4_c`      | §14.3            | Full 4x4 inverse Walsh–Hadamard for the Y2 DC-of-DC block.    |
| `vp8_short_inv_walsh4x4_1_c`    | §14.3 (fast path)| Fast WHT path when only the WHT DC is non-zero.               |

All four are exposed through the RTCD layer in
`vp8/common/rtcd_defs.pl:115–128`; they are the C fall-backs that any
architecture without a hand-written SIMD specialization gets at run
time.

The file does not allocate, does not call into the rest of libvpx,
and has no per-frame state. Its only `#include` is
`vp8_rtcd.h`, which is generated by Perl from `rtcd_defs.pl`
and contains the function-pointer prototypes plus the
`#define`s that pick a specialization. That keeps the module
single-purpose: pure functions on coefficient and pixel arrays.

## The two magic constants

```c
static const int cospi8sqrt2minus1 = 20091;
static const int sinpi8sqrt2       = 35468;
```

These are the only two multiply constants used by the 4x4 IDCT
butterfly. The numerical values come straight from RFC 6386 §14.2:

```
cospi8sqrt2minus1 = round((cos(π/8) · √2 − 1) · 2^16) = 20091
sinpi8sqrt2       = round( sin(π/8) · √2          · 2^16) = 35468
```

VP8's transform is an *approximation* of an 8-bit-input 4-point DCT.
The exact DCT requires irrational multipliers; the spec quantises them
into these two 16.16-style integer constants and *declares them
normative*. Every decoder must compute with these exact integers — a
decoder using "more accurate" constants would produce a different
reconstruction and drift away from the encoder's prediction loop.

The file's comment explains the subtlety:

```text
* Becuase the first constant is bigger than 1, to maintain the same 16 bit
* fixed point precision as the second one, we use a trick of
*         x * a = x + x*(a-1)
```

`sin(π/8)·√2 ≈ 0.5412` fits in 16-bit unsigned fixed point with no
loss (`35468 / 2^16 = 0.5412`). But `cos(π/8)·√2 ≈ 1.3066` does not —
it would overflow a Q16 representation. The encoder/decoder factor it
as `1 + 0.3066` and only store the fractional part (`20091 / 2^16 =
0.3066`). At evaluation time the multiplication

```c
ip[4] + ((ip[4] * cospi8sqrt2minus1) >> 16)
```

reconstructs `ip[4] * cos(π/8)·√2` with the same Q16 precision as
`(ip[12] * sinpi8sqrt2) >> 16` — both products are then in the
*pixel-value* domain rather than a scaled one, so they can be added and
subtracted directly with no rescaling. The typo "Becuase" is in the
original source; preserved here for findability.

## The 4x4 IDCT: `vp8_short_idct4x4llm_c`

This is the workhorse called once per residual 4x4 block whenever
`eobs[block] > 1`. The signature is:

```c
void vp8_short_idct4x4llm_c(short *input, unsigned char *pred_ptr,
                            int pred_stride, unsigned char *dst_ptr,
                            int dst_stride);
```

`input` points at 16 `short` dequantized coefficients laid out row-major
in a 4x4 grid; `pred_ptr / pred_stride` is the predictor (intra or
inter) for those 16 samples; `dst_ptr / dst_stride` is where the
clamped reconstruction is written. The function does *not* zero
`input` — the caller (or the SIMD variant) is responsible for that if
the buffer is reused.

### Invariants and layout

The coefficient buffer has stride 4 (the local `shortpitch = 4`
variable), so column `c` of the input is at `input[c]`, `input[4+c]`,
`input[8+c]`, `input[12+c]`. Throughout the routine, indices `0, 4, 8,
12` step *down a column*, and `0, 1, 2, 3` step *across a row*. The
caller (`vp8_dequantize_b` followed by `vp8_short_idct4x4llm`,
typically reached through `vp8_dequant_idct_add_c`) guarantees that
the coefficient magnitudes stay well within `short` range after the
butterfly grows them, because the dequant tables in
`vp8/common/quant_common.c` are themselves bounded.

### The butterfly

The 4-point inverse DCT factors into two butterflies. Define

```
a = x0 + x2          (DC + second-DC : low-frequency sum)
b = x0 − x2          (DC − second-DC : low-frequency diff)
c = x1·sin(π/8)·√2 − x3·cos(π/8)·√2    (high-frequency)
d = x1·cos(π/8)·√2 + x3·sin(π/8)·√2    (high-frequency)
```

then the four outputs are `a+d, b+c, b−c, a−d`. That is precisely
what the inner loops compute:

```c
a1 = ip[0] + ip[8];
b1 = ip[0] - ip[8];

temp1 = (ip[4] * sinpi8sqrt2) >> 16;
temp2 = ip[12] + ((ip[12] * cospi8sqrt2minus1) >> 16);
c1 = temp1 - temp2;

temp1 = ip[4] + ((ip[4] * cospi8sqrt2minus1) >> 16);
temp2 = (ip[12] * sinpi8sqrt2) >> 16;
d1 = temp1 + temp2;

op[shortpitch * 0] = a1 + d1;
op[shortpitch * 3] = a1 - d1;
op[shortpitch * 1] = b1 + c1;
op[shortpitch * 2] = b1 - c1;
```

Here `ip[0], ip[4], ip[8], ip[12]` are the four samples of one
*column* (vertical stride 4 in a 4-wide row-major buffer); on the
second pass `ip[0..3]` are the four samples of one *row*. Each
multiplication by the (a−1)-encoded cosine is reconstructed as the
`x + ((x*const)>>16)` pattern; each sine multiplication is the plain
`(x*const)>>16`.

### Row pass, column pass

The function performs the IDCT *separably*: first a column pass, then
a row pass. The first loop iterates `i = 0..3` and, on each iteration,
treats `ip[0], ip[4], ip[8], ip[12]` (vertical stride) as the input
column and writes into `op[0], op[4], op[8], op[12]`. The post-loop
`ip++; op++;` walks to the next column. Output sits in the local
`output[16]` buffer.

The second loop reseats `ip = output; op = output;` and now runs *in
place* over rows: the indices step `ip[0], ip[1], ip[2], ip[3]`
(horizontal stride 1) and `ip += shortpitch` after each iteration.
This is the row pass. Note the structural symmetry — the two passes
share the same butterfly; only the strides differ.

### Rounding and the `>> 3`

After the row pass the values are still scaled. The forward 4-point
DCT VP8 uses introduces a factor of 8 across the two passes (each pass
contributes a factor of 2 by way of the `a±b` butterflies and a
further factor reflected in the cosine scaling); to undo it, the row
pass divides by 8. That is the meaning of:

```c
op[0] = (a1 + d1 + 4) >> 3;
```

The `+4` is symmetric rounding (`+ (1 << 2)` for a `>> 3`), keeping
the average error centered on zero. There is no further shift after
the column pass — the scaling factor is absorbed in one place at the
end.

### Summation with the predictor

The last loop is where this kernel actually *touches the picture*:

```c
for (r = 0; r < 4; ++r) {
  for (c = 0; c < 4; ++c) {
    int a = ip[c] + pred_ptr[c];
    if (a < 0) a = 0;
    if (a > 255) a = 255;
    dst_ptr[c] = (unsigned char)a;
  }
  ip += 4;
  dst_ptr += dst_stride;
  pred_ptr += pred_stride;
}
```

That is RFC 6386 §14.4 verbatim: clip-to-`[0, 255]` the per-sample
sum of the inverse-transformed residue and the predictor, and write
the result into the destination frame. `pred_stride` and `dst_stride`
are independent because the predictor for an intra block is normally
inside a small scratch buffer (`xd->predictor`, 24 bytes wide for the
16x16 luma block) while the destination is the YV12 luma plane with
its full frame stride. The inter path can use `dst_ptr == pred_ptr`
(the predictor was written directly to the destination by the
motion-compensated sub-pixel filter); both stride arguments then carry
the same value.

The `<0` and `>255` checks are necessary because the residual sum can
saturate either side: a strongly-negative residue plus a low predictor
can underflow, a strongly-positive residue plus a high predictor can
overflow. This clip is mandatory — the spec defines the reconstructed
pixel as the *clipped* sum, not the raw sum.

## DC-only fast path: `vp8_dc_only_idct_add_c`

When the entropy decoder reports `eobs[block] == 1`, only the DC
coefficient is non-zero (zigzag position 0). The full butterfly
collapses: the only non-zero contribution to every output sample is
`(dc + 4) >> 3`, the same constant for all 16 positions.

```c
int a1 = ((input_dc + 4) >> 3);
```

The signature takes the *already-dequantized* DC value directly as
`short input_dc`, not a pointer to a buffer — that lets the dispatch
in `vp8/common/idct_blk.c:24` precompute `q[0] * dq[0]` once without
touching the rest of the coefficient buffer:

```c
vp8_dc_only_idct_add_c(q[0] * dq[0], dst, stride, dst, stride);
memset(q, 0, 2 * sizeof(q[0]));
```

The `+4` rounding matches the full path: the same `>> 3` is applied
because the same forward-transform scaling needs to be undone. The
clip-and-add inner loop is identical to the full IDCT's last loop;
only the residue value changes from per-sample to a single broadcast
constant. The `memset` clears the DC and the next coefficient slot
(positions 0 and 1) so subsequent reads of the residue buffer see
zeros — important because some neighbour-context probability paths in
the entropy decoder inspect the *previous* coefficient magnitude when
they walk into adjacent blocks.

This path is hit very often: for typical content many residual blocks
have one non-zero coefficient or none, so a dedicated kernel pays for
itself. The "or none" case (`eobs == 0`) is handled even further
upstream — `vp8_dequant_idct_add_y_block` simply skips both kernels
and leaves `dst` equal to the predictor.

## The Y2 / Walsh–Hadamard path

The reason the Walsh kernels live in this same file is that they are
the *companion* transform of the IDCT: where the IDCT runs over a
single 4x4 of luma or chroma residual, the WHT runs over the 4x4
*grid of luma DCs* across the macroblock. The two transforms are
applied in sequence — first WHT, then 16 IDCTs.

### Why a second-order transform at all

In a macroblock predicted as a single 16x16 block (i.e., its mode is
neither `B_PRED` nor `SPLITMV`), the 16 luma 4x4 sub-blocks share
much of the slow-varying brightness. The 16 DC coefficients of those
4x4 IDCTs are therefore strongly correlated — they roughly form a
smooth 4x4 image of their own. The encoder exploits this by running a
*second-order* Hadamard over those 16 DCs and coding only the
transformed values (the "Y2" or "DC of DC" block, block 24 in the
macroblock layout — see `vp8_technical_overview.md` §4.2 and the
`block[25]` array declared in
`vp8/common/blockd.h:221`). On the encode side the per-Y-block DCs
are *zeroed* and the 16-element WHT output is what gets quantized and
entropy-coded.

The decoder runs the inverse: decode block 24's 16 WHT coefficients,
invert the WHT to recover the 16 luma DCs, *scatter* them back into
the DC slot of each of the 16 Y residual blocks, then run the per-block
IDCTs as usual. The scatter is the `mb_dqcoeff[i * 16] = output[i]`
loop at the bottom of `vp8_short_inv_walsh4x4_c` (lines 172–174):
position 0 of the i-th 4x4 coefficient block (each occupying 16
shorts in `xd->qcoeff`) is overwritten with output sample `i`. After
this, the per-Y-block IDCT path is the same as for any other block —
the rest of the coefficients (the AC positions 1..15) were already
parsed from the bitstream with `block_type = 0` ("Y after Y2 AC"),
starting from zigzag band 1 (`vp8_technical_overview.md` §9.3).

### `vp8_short_inv_walsh4x4_c`

The signature exposes both ends of the pipeline at once:

```c
void vp8_short_inv_walsh4x4_c(short *input, short *mb_dqcoeff);
```

`input` is the dequantized WHT coefficient block — caller passes
`&xd->block[24].dqcoeff[0]`. `mb_dqcoeff` is the *full macroblock*
coefficient buffer `xd->qcoeff[400]`; the function strides through it
by 16 to place one recovered DC into each Y block.

Like the IDCT, the WHT is separable in two passes. Unlike the IDCT,
the butterfly is pure ±1: no multiplications, no rounding inside the
pass, just sums and differences:

```c
/* column pass: */
a1 = ip[0] + ip[12];
b1 = ip[4] + ip[8];
c1 = ip[4] - ip[8];
d1 = ip[0] - ip[12];

op[0] = a1 + b1;
op[4] = c1 + d1;
op[8] = a1 - b1;
op[12] = d1 - c1;
```

That is RFC 6386 §14.3's exact butterfly. The row pass uses identical
arithmetic with horizontal stride; it then divides by 8 with `+3`
rounding (note: **`+3`**, not `+4` — the WHT has a different forward
scaling than the DCT, which results in a slightly asymmetric rounding
offset). The final loop scatters into the DC slots, completing the
"hand the DCs back to the IDCT" step.

### `vp8_short_inv_walsh4x4_1_c`

This is the WHT analog of `vp8_dc_only_idct_add`: when the Y2 block
has exactly one non-zero coefficient — the WHT's own DC — every
output sample is `(input[0] + 3) >> 3`, and the scatter degenerates
to a constant broadcast:

```c
a1 = ((input[0] + 3) >> 3);
for (i = 0; i < 16; ++i) {
  mb_dqcoeff[i * 16] = a1;
}
```

That is: every Y block gets the same DC. Physically this corresponds
to a macroblock whose luma is well-modeled by a single brightness
offset on top of the predictor. The dispatch at
`vp8/decoder/decodeframe.c:208–215` picks between the two WHT routines
on the value of `eobs[24]`, mirroring the IDCT's split on `eobs[i]`:

```c
if (xd->eobs[24] > 1) {
  vp8_dequantize_b(b, xd->dequant_y2);
  vp8_short_inv_walsh4x4(&b->dqcoeff[0], xd->qcoeff);
} else {
  b->dqcoeff[0] = (short)(b->qcoeff[0] * xd->dequant_y2[0]);
  vp8_short_inv_walsh4x4_1(&b->dqcoeff[0], xd->qcoeff);
}
```

Note that the Y2 block uses its own dequant tables (`dequant_y2[]`)
with the `y2dc_delta_q` and `y2ac_delta_q` offsets applied — see
`vp8_technical_overview.md` §9.4.

### Interaction with the per-block IDCTs

The Y2 path runs *before* `vp8_dequant_idct_add_y_block`. The
sequence (`vp8/common/invtrans.h:36–52` for the encoder-side reference,
or `vp8/decoder/decodeframe.c:200–226` for the decoder driver) is:

1. If the MB has a Y2 block (mode is neither `B_PRED` nor `SPLITMV`):
   call `vp8_short_inv_walsh4x4` (or its `_1` fast path) to seed
   `xd->qcoeff[0]`, `xd->qcoeff[16]`, `xd->qcoeff[32]`, … with the
   recovered DCs of the 16 Y blocks.
2. Adjust `eobs` (see `eob_adjust` in `invtrans.h`): if a Y block had
   `eobs == 0` from token decode but the WHT just delivered a non-zero
   DC into its slot, bump the `eob` to 1 so that the IDCT dispatch
   chooses the DC-only path rather than skipping the block entirely.
3. Switch the Y dequant table to `dequant_y1_dc`, which is the same as
   `dequant_y1` *except for position 0* — that one is set to 1 so the
   already-dequantized DC from the WHT isn't dequantized twice when
   `vp8_dequant_idct_add` multiplies `q[k] * dq[k]`.
4. Call `vp8_dequant_idct_add_y_block`, which now runs the 4x4 IDCT
   on each Y block (with the WHT-seeded DC and the entropy-decoded
   ACs) and accumulates into the luma plane.

When the MB has no Y2 (`B_PRED` or `SPLITMV`), this whole dance is
skipped: the Y blocks were decoded with `block_type = 3` ("Y, no Y2")
and they carry their own DCs already, so the per-block IDCT runs
directly with `dequant_y1`.

The UV path never has a Y2 — chroma blocks are decoded with
`block_type = 2`, always starting from zigzag band 0, and
`vp8_dequant_idct_add_uv_block` calls only the IDCT routines from this
file.

## Mapping the file to RFC 6386

| File location                 | RFC 6386 section                  | What it implements                                 |
|-------------------------------|-----------------------------------|----------------------------------------------------|
| `idctllm.c:26–27`             | §14.2 (the two normative consts)  | `cospi8sqrt2minus1`, `sinpi8sqrt2`                 |
| `idctllm.c:29–103`            | §14.2 + §14.4                     | Full 4x4 IDCT followed by predictor summation/clip |
| `idctllm.c:105–125`           | §14.2 (fast path)                 | DC-only IDCT-add                                   |
| `idctllm.c:127–175`           | §14.3                             | Inverse WHT for Y2                                 |
| `idctllm.c:177–185`           | §14.3 (fast path)                 | DC-only inverse WHT                                |

Together they constitute the *entire* transform inversion the VP8
standard requires — there are no other 8x8 or 16x16 transforms in
VP8, only this one 4x4 IDCT applied 24 times per macroblock (16 luma +
4 U + 4 V) and optionally the one Walsh applied once at the
macroblock level. That economy is one of VP8's defining design
choices, and it is why this small file is hot enough to justify the
SIMD specializations declared next to it in `rtcd_defs.pl`.
