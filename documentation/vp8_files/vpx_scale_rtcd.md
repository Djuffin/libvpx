# `vpx_scale/vpx_scale_rtcd.c` — the once-only initialiser for the YV12 scaler dispatch table

`vpx_scale_rtcd.c` is a perfect twin of `vp8/common/rtcd.c` and
`vpx_dsp/vpx_dsp_rtcd.c`. Counting the licence header it is sixteen
lines long; stripped of boilerplate it is exactly two lines of code.
Yet, in the same way its siblings own the dispatch table for VP8's
pixel kernels and for the generic DSP layer, this file owns the
dispatch table for the *YV12 frame-buffer* operations — the border
extender, the full-frame copier, and the luma-plane copier. Every call
in the VP8 decoder that has to copy a reference frame, or replicate the
last row/column of pixels into the border so that motion-compensated
prediction can sample beyond the picture edge, ultimately resolves to a
symbol whose definition was emitted into this translation unit by the
generated header `vpx_scale_rtcd.h`.

```c
#include "./vpx_config.h"
#define RTCD_C
#include "./vpx_scale_rtcd.h"
#include "vpx_ports/vpx_once.h"

void vpx_scale_rtcd(void) { once(setup_rtcd_internal); }
```

That is the entire file. Everything else interesting about it is what
the preprocessor and the libvpx build system make happen *around* those
lines.

## Role in the decoder

`RTCD` is libvpx's own acronym for **Run-Time CPU Dispatch**: a single
binary that may, at first use, replace each accelerable kernel's
function pointer with the best implementation the current CPU supports
(NEON on ARM, SSE2/SSSE3/AVX2 on x86, MSA on MIPS, LSX on LoongArch,
DSPR2 specifically for the YV12 border extender on certain MIPS
targets, and so on). Libvpx maintains three such dispatch tables, each
generated by `build/make/rtcd.pl` from a tiny Perl DSL:

  * `vp8_rtcd.h`/`vp8/common/rtcd.c` — VP8-specific kernels
    (sixtap/bilinear sub-pixel filters, 4x4 IDCT, loop filter, dequant
    helpers, copy_mem).
  * `vpx_dsp_rtcd.h`/`vpx_dsp/vpx_dsp_rtcd.c` — codec-agnostic DSP
    (intra-predictors, bitreader inner loops, variance/SAD for the
    encoder, …).
  * `vpx_scale_rtcd.h`/`vpx_scale/vpx_scale_rtcd.c` — **this file's
    table**: the YV12 buffer operations that bridge the codec to the
    frame-buffer manager.

This file is the *vpx_scale-side* initialiser of that third table. In
exactly the same way as its siblings, it is reduced to a single
statement that hands the entire job over to a generated header.

### What the YV12 dispatch table contains

The DSL that drives the generator is `vpx_scale/vpx_scale_rtcd.pl`. On
the verified `generic-gnu` single-arch decoder build
(`--disable-spatial-resampling`, no SIMD), the resulting header
declares three primitives:

```c
// vp8_only/vpx_scale_rtcd.h
void vp8_yv12_copy_frame_c(const struct yv12_buffer_config *src_ybc,
                           struct yv12_buffer_config *dst_ybc);
#define vp8_yv12_copy_frame vp8_yv12_copy_frame_c

void vp8_yv12_extend_frame_borders_c(struct yv12_buffer_config *ybf);
#define vp8_yv12_extend_frame_borders vp8_yv12_extend_frame_borders_c

void vpx_yv12_copy_y_c(const struct yv12_buffer_config *src_ybc,
                       struct yv12_buffer_config *dst_ybc);
#define vpx_yv12_copy_y vpx_yv12_copy_y_c
```

Three primitives, plus the public initialiser:

```c
void vpx_scale_rtcd(void);
```

The reference C implementations of all three live in
`vpx_scale/generic/yv12extend.c` (lines 105, 193 and 311 respectively).
On a build with `CONFIG_SPATIAL_RESAMPLING=yes`, the DSL adds seven
more entries for the 5:4, 5:3 and 2:1 horizontal/vertical band scalers
used by the encoder's spatial-resampler — none of which is reached by
the decoder. On a build with `CONFIG_VP9=yes`, three further VP9-only
entries appear (`vpx_yv12_copy_frame`, `vpx_extend_frame_borders`,
`vpx_extend_frame_inner_borders`, two of which carry a `dspr2`
specialisation). The decoder-only VP8 build sees none of those: the
table is at its minimum size and `setup_rtcd_internal` is *empty*.

```c
// vp8_only/vpx_scale_rtcd.h
#ifdef RTCD_C
static void setup_rtcd_internal(void)
{
}
#endif
```

The point of this file, then, is not what `setup_rtcd_internal`
*does* on this configuration — nothing — but that the file exists at
all, so that the symbol is *defined* somewhere and so that the
once-only protocol is honoured. On a richer build (say
`mips32-linux-gcc` with `CONFIG_VP9=yes`) the same translation unit
would emit a body that calls `mips_cpu_caps()` and overrides
`vpx_extend_frame_borders` with `vpx_extend_frame_borders_dspr2`. The
client code at the call site is unchanged either way.

### Who calls `vpx_scale_rtcd()`

The VP8 decoder calls it exactly where it calls `vp8_rtcd()` and
`vpx_dsp_rtcd()` — from the codec-create paths in `vp8_dx_iface.c` and
`onyxd_if.c`, by way of `vp8/common/generic/systemdependent.c`. The
three calls always appear together:

```c
vp8_rtcd();
vpx_dsp_rtcd();
vpx_scale_rtcd();
```

After these return, the entire VP8 decoder pipeline — IDCT, sub-pixel
filtering, loop filter, intra prediction, bitreader inner loops, and
YV12 border extension/copy — is bound to its best available
implementation for this host. There is no further dispatch cost beyond
one indirect call per kernel invocation on builds that actually have
multiple implementations to choose between, and zero cost on builds
where the `#define` aliases collapsed everything at compile time.

### Why the YV12 layer gets its own table

A reasonable question is why the three border/copy primitives are not
simply lumped into `vp8_rtcd.h` along with the sixtap filters and the
IDCT. The reason is that `vpx_scale_rtcd.h` is shared between VP8 and
VP9 (the VP9 codec also extends and copies YV12 buffers, and one of its
specialisations — `vpx_extend_frame_borders_dspr2` — is unique to the
YV12 layer). Keeping the scaler primitives in a separate file lets a
VP9-only build link the scaler table without dragging in the VP8 DSL,
and lets a VP8-only build (as documented in `vp8_files.md`) link a
trimmed-down version with only three entries. The same architectural
reason explains why `vpx_dsp_rtcd.c` and `vp8_rtcd.c` are kept
separate: each table is owned by the layer that defines its DSL, and
each is initialised by its layer's own `*_rtcd()` entry point.

## The file's contents, line by line

```c
#include "./vpx_config.h"
#define RTCD_C
#include "./vpx_scale_rtcd.h"
#include "vpx_ports/vpx_once.h"

void vpx_scale_rtcd(void) { once(setup_rtcd_internal); }
```

### `#include "./vpx_config.h"`

**What.** Brings in the configure-time feature macros — `CONFIG_*`
(such as `CONFIG_MULTITHREAD`, `CONFIG_SPATIAL_RESAMPLING`,
`CONFIG_VP9`) and `HAVE_*` (such as `HAVE_PTHREAD_H`, `HAVE_DSPR2`).

**Why.** This file does not reference any such macro directly. But
both of the headers that follow do: `vpx_scale_rtcd.h` reads
`CONFIG_SPATIAL_RESAMPLING` and `CONFIG_VP9` (via the DSL output) and
the `HAVE_*` flags that gate each specialisation; `vpx_once.h` reads
`CONFIG_MULTITHREAD` and `HAVE_PTHREAD_H` to decide which `once()`
implementation to emit. Including `vpx_config.h` first guarantees both
have a consistent view of the configuration. The pattern — *config
first, generated header second, port glue third* — is the same one
used by `vp8/common/rtcd.c` and `vpx_dsp/vpx_dsp_rtcd.c`.

**Invariant.** `vpx_config.h` must be a generated header, produced by
`./configure`, that exists in the include path before `vpx_scale_rtcd.h`
is parsed.

**How used.** Indirectly, by the two headers that follow.

### `#define RTCD_C`

**What.** A single token define, set with no replacement value. The
generated header `vpx_scale_rtcd.h` checks for it:

```c
#ifdef RTCD_C
#define RTCD_EXTERN
#else
#define RTCD_EXTERN extern
#endif
```

and again, later:

```c
#ifdef RTCD_C
static void setup_rtcd_internal(void)
{
    /* generated body */
}
#endif
```

**Why.** This single macro is what makes *this* translation unit the
"owner" of the YV12 dispatch table. With `RTCD_C` defined, the header
(a) emits the pointer-table definitions (`RTCD_EXTERN` collapses to
nothing, so each `RTCD_EXTERN void (*foo)(…)` line becomes a definition
rather than a declaration) and (b) emits `setup_rtcd_internal` as a
`static` function body. Without `RTCD_C`, the same header emits
`extern` declarations of the pointers and omits `setup_rtcd_internal`
entirely. There must therefore be **exactly one** translation unit per
RTCD table that defines `RTCD_C` before the include, and that file
must do nothing else (else it would carry undefined references to its
own siblings). `vpx_scale_rtcd.c` is the one such file for the YV12
table.

**Invariant.** No other .c file in the build defines `RTCD_C` before
including `vpx_scale_rtcd.h`. If one did, either the linker would see
two static `setup_rtcd_internal` definitions (silently fine, because
`static` makes them file-local) or — more annoyingly on SIMD builds —
two definitions of the same pointer (which `RTCD_EXTERN` would expand
to definitions in both). The convention is that exactly one .c file
per table defines `RTCD_C`, and that file's body is `once(setup)`.

**Order.** The `#define` must come *before* the `#include` of
`vpx_scale_rtcd.h`; otherwise the wrong branches of the `#ifdef RTCD_C`
guards are taken and `vpx_scale_rtcd()` would compile a reference to a
`setup_rtcd_internal` that is never defined — a link-time failure.

### `#include "./vpx_scale_rtcd.h"`

**What.** Pulls in the generated header that contains the prototypes,
the (possibly empty) pointer table, and the conditional definition of
`setup_rtcd_internal`. The header itself is produced by
`build/make/rtcd.pl` from `vpx_scale/vpx_scale_rtcd.pl` at
configure/build time; the libvpx repository never commits it.

**Why.** This is the whole point of the file. The include drags in
the `static void setup_rtcd_internal(void) { … }` body that `once()`
will refer to, and (on SIMD builds) defines the function pointers that
the body will populate. On a `generic-gnu` decoder build the included
text is the abridged form shown above: three `#define` aliases and an
empty initialiser body. On a SIMD-enabled VP9 build it is roughly:

```c
void vpx_extend_frame_borders_c(struct yv12_buffer_config *ybf);
void vpx_extend_frame_borders_dspr2(struct yv12_buffer_config *ybf);
RTCD_EXTERN void (*vpx_extend_frame_borders)(struct yv12_buffer_config *);

static void setup_rtcd_internal(void)
{
    int flags = mips_cpu_caps();
    vpx_extend_frame_borders = vpx_extend_frame_borders_c;
    if (flags & HAS_DSPR2)
        vpx_extend_frame_borders = vpx_extend_frame_borders_dspr2;
    /* … */
}
```

**Path style.** The leading `./` forces the compiler's
"current-directory-of-the-including-file" rule. In libvpx,
`vpx_scale_rtcd.h` is *generated* into the build directory (e.g.
`build_debug/vpx_scale_rtcd.h`, `vp8_only/vpx_scale_rtcd.h`), not
committed; the build system arranges the include path so that "current
directory" resolves to that build directory. The `./` prefix is the
libvpx convention for "this header is generated next to the .c file"
and is used identically in `vp8/common/rtcd.c` and
`vpx_dsp/vpx_dsp_rtcd.c`.

**Invariant.** The generator has already run; `vpx_scale_rtcd.h`
exists somewhere on the include path; and the same `vpx_config.h` was
in scope when it was generated. (The DSL inspects `vpx_config(...)` at
generation time, so the header's *content* depends on the build's
configuration.)

### `#include "vpx_ports/vpx_once.h"`

**What.** Provides the `static void once(void (*func)(void))` helper
that wraps `setup_rtcd_internal` in a thread-safe, first-caller-wins
guard.

**Why.** Multiple decoder instances may be created concurrently — by
two threads of a server process, by two `vpx_codec_dec_init_ver()`
calls in flight at once, by a fuzzing harness exercising the create
path. Each invokes `vpx_scale_rtcd()`. Without protection, on a SIMD
build, two threads would race to overwrite the same pointer table
(harmless on architectures where pointer stores are atomic, but
undefined behaviour in C and visibly racy under TSAN). `once()` makes
the first caller of `vpx_scale_rtcd()` the winner, blocks all others
until it returns, and short-circuits every subsequent call.

`vpx_once.h:16-37` documents an essential limitation:

> These functions use static locks, and can only be used with one
> common argument per compilation unit.

That is, *each .c file* that includes `vpx_once.h` gets its own
file-static lock (via the `static` qualifier on `once` itself), so
`vpx_scale_rtcd.c`'s `once()` has one lock state, `vp8/common/rtcd.c`'s
`once()` has another, and `vpx_dsp/vpx_dsp_rtcd.c`'s `once()` has a
third. None can starve another, and each must be called with at most
one distinct function argument in its translation unit. This file
obeys the rule trivially — `once()` is invoked exactly once, with
exactly one argument, on exactly one line.

**Invariant.** `vpx_once.h`'s selection of implementation (the Win32
`InterlockedCompareExchange` loop, `pthread_once`, or the
single-threaded `static volatile int done` flag) matches the
build's threading model. That choice is made entirely at preprocessor
time by `vpx_once.h:40-114`, gated on `CONFIG_MULTITHREAD` and
`HAVE_PTHREAD_H` — both of which were brought in by `vpx_config.h`
above.

### `void vpx_scale_rtcd(void) { once(setup_rtcd_internal); }`

**What.** The public entry point of the YV12 dispatch subsystem. Its
prototype is emitted by the generated header
(`vpx_scale_rtcd.h:36`), so any compilation unit that includes
`./vpx_scale_rtcd.h` can call it; its definition lives here, and only
here, in the entire codec.

**Why this shape.** Identical reasoning to `vp8/common/rtcd.c`. Three
overlapping reasons make this one-liner unavoidable:

  1. `setup_rtcd_internal` is *generated* into the header, not written
     by hand. The whole reason this .c file exists is to be the one
     translation unit into which that generated static body is emitted.
     Putting anything substantive into `vpx_scale_rtcd.c` would force a
     copy of the generated boilerplate into the source tree, defeating
     the code-generation strategy.

  2. The `once()` wrapper has to *enclose* the call site, because the
     synchronisation primitive (`pthread_once`, the Win32
     `InterlockedCompareExchange` loop, or the C-only fallback) is
     selected by `vpx_once.h` based on configure-time flags. Keeping
     that selection in `vpx_once.h`, and keeping `vpx_scale_rtcd()`
     ignorant of it, is what lets libvpx be built for Windows, glibc
     Linux, musl Linux, Apple, Android (bionic) and bare-metal SDKs
     without touching a line of this file.

  3. `once()` is a *file-static* function. Each translation unit that
     includes `vpx_once.h` gets its own copy of the lock state. That is
     exactly what is wanted: `vpx_scale_rtcd.c`'s `once()` has its own
     lock, distinct from `vp8/common/rtcd.c`'s and from
     `vpx_dsp/vpx_dsp_rtcd.c`'s. Initialising any one of the three
     tables does not delay initialising the other two.

**Invariants.**

  * `vpx_scale_rtcd()` is **safe to call from any thread at any time**
    after process start. The synchronisation within `once()` makes the
    first-call/subsequent-call distinction transparent to the caller.
  * `vpx_scale_rtcd()` is **idempotent**. On every implementation,
    second and later calls are no-ops; on the C-only fallback,
    `vpx_once.h:101-115` makes this idempotency explicit ("`*_rtcd()`
    is idempotent, so as long as your platform provides atomic
    loads/stores of pointers no synchronization is strictly
    necessary"). The fallback exploits that fact by skipping
    synchronisation entirely.
  * `vpx_scale_rtcd()` **must be called before** any of the dispatched
    primitives — `vp8_yv12_extend_frame_borders`,
    `vp8_yv12_copy_frame`, `vpx_yv12_copy_y` — is invoked. On the
    `generic-gnu` decoder build, where each is a `#define` alias to its
    `_c` reference, this is trivially satisfied; on a SIMD build it is
    a real requirement upheld by the codec-create paths in
    `vp8_dx_iface.c` and `onyxd_if.c`.
  * `vpx_scale_rtcd()` **must not be called from a signal handler**:
    POSIX `pthread_once` is async-signal-safe, but the Win32
    implementation uses `Sleep(0)` to yield (`vpx_once.h:82`), which is
    not. The codec APIs themselves are not signal-safe either, so this
    constraint is normally invisible.

**How used.** From the decoder-create path, alongside its two
siblings, before any frame is decoded:

```c
vp8_rtcd();        /* VP8 kernels */
vpx_dsp_rtcd();    /* generic DSP */
vpx_scale_rtcd();  /* YV12 buffer ops */
```

That single call binds `vp8_yv12_extend_frame_borders` (called from
`vp8/common/extend.c` and from `vp8/decoder/decodeframe.c` after every
decoded frame, to replicate edge pixels into the 32-sample border for
the next frame's motion compensation), `vp8_yv12_copy_frame` (called
from `vp8/common/swapyv12buffer.c` and the reference-frame management
logic to duplicate one YV12 buffer into another), and `vpx_yv12_copy_y`
(called when only the luma plane needs to be propagated) to their best
available implementations.

## How the pieces fit together at runtime

The request "decode the first VP8 frame in this process" causes the
following chain of events, with respect to this file specifically:

  1. The caller (`vpx_codec_dec_init_ver` → `vp8_init_decoder` →
     ultimately `vp8_create_common`) invokes `vpx_scale_rtcd()`.
  2. `vpx_scale_rtcd()` calls `once(setup_rtcd_internal)`. The
     `once` symbol is the file-static one from this translation unit;
     the lock state it consults is this file's and no one else's.
  3. On the very first such call ever in the process, `once()`
     acquires its lock (or wins the `InterlockedCompareExchange`, or
     sets `done = 1`, depending on the build) and invokes
     `setup_rtcd_internal`.
  4. `setup_rtcd_internal` is the symbol that the generated
     `vpx_scale_rtcd.h` defined under `#ifdef RTCD_C`. Because
     `vpx_scale_rtcd.c` is the only translation unit with `RTCD_C`
     defined at the point of inclusion, this is the *only* place in
     the program where `setup_rtcd_internal` exists as a defined
     symbol. (The `static` qualifier means even if another file
     accidentally defined `RTCD_C` and included the header, there
     would be two distinct file-local symbols rather than a
     multiple-definition link error — but the convention is one .c per
     table.)
  5. `setup_rtcd_internal` runs through whatever assignment blocks the
     generator emitted. On the verified `generic-gnu` decoder build the
     body is empty — there is literally nothing to do, because every
     pointer was preempted by a `#define` alias at compile time. On a
     SIMD-enabled VP9 build the body queries the appropriate
     `*_cpu_caps()` and writes pointers like
     `vpx_extend_frame_borders = vpx_extend_frame_borders_dspr2;`.
  6. `once()` returns; `vpx_scale_rtcd()` returns; the caller continues
     with decoder setup. On every subsequent call to `vpx_scale_rtcd()`
     — from this thread, a sibling thread, or an unrelated decoder
     instance created hours later — `once()` short-circuits and
     returns immediately, with no observable cost beyond a load of the
     `done`/`once_state` flag.

## Why this file is *not* simply replaced by a constructor

A reasonable refactoring proposal is: instead of having clients call
`vpx_scale_rtcd()` from the codec-create path, use a GCC/Clang
`__attribute__((constructor))` (or the C++11 static-object trick) to
run `setup_rtcd_internal` automatically at library load time, and
remove `vpx_scale_rtcd()` from the public surface entirely.

Libvpx chooses not to do this for a portability reason: not every
target it supports has constructor attributes (`__attribute__` is GNU,
MSVC needs a different mechanism, certain embedded toolchains have
neither), and the cost paid at the call site of `vpx_scale_rtcd()` —
one indirect call, one lock-state load — is small enough that the
explicit call is preferable to a per-toolchain constructor strategy.
The result is that this file's six-line body is the entire mechanism,
in every build, on every platform.

## Summary

This is the smallest non-trivial translation unit in the YV12 layer.
It exists for three connected reasons: to be the *unique* `RTCD_C`
owner of `vpx_scale_rtcd.h` (so the pointer table and
`setup_rtcd_internal` have exactly one definition site); to bind that
generated initialiser to the once-only synchronisation primitive from
`vpx_ports/vpx_once.h` (so a single call from any thread is sufficient
to set up the table, and concurrent calls do not race); and to expose
the call as a public entry point `vpx_scale_rtcd()` that codec-create
paths can invoke alongside their two siblings `vp8_rtcd()` and
`vpx_dsp_rtcd()`. On the verified `generic-gnu` VP8-only decoder
build, the table has three entries (`vp8_yv12_extend_frame_borders`,
`vp8_yv12_copy_frame`, `vpx_yv12_copy_y`), all three collapse to
`#define` aliases of their `_c` reference implementations in
`vpx_scale/generic/yv12extend.c`, and `setup_rtcd_internal` is empty.
The file pays the same price either way: one synchronised function
call, exactly once per process, with no further work to do.
